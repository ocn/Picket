# 02 — Fleet Composition Tally splits out Type-Tracked Ships with slot priority

**What to build:** The Fleet Composition Tally — the overall category lines and the per-affiliation breakdown lines — tallies Type-Tracked Ships under their Ship Type name, apart from their Ship Group, with no double counting: a kill with two tracked Sidewinders and a Buzzard matched only by group renders "2x Sidewinder, 1x CovOps". Type entries claim the named slots in each category line ahead of the existing count-based selection, so a tracked hull is never buried in the "+N" overflow behind larger blob groups. Type entries sort at their parent Ship Group's display position, classify into supers/caps/subcaps by their parent group, and render singular. Group-only subscriptions produce byte-identical tallies. The two-named-entries-plus-overflow structure and all line formatting are unchanged. Reuses the Type-Tracked Ship rule from ticket 01. See `.scratch/ship-type-name-display/spec.md`.

**Blocked by:** 01 — Title shows the Ship Type name for Type-Tracked Ships (shared Type-Tracked Ship rule).

**Status:** resolved

- [x] A mixed fixture kill renders type and group Tally Entries side by side with counts that sum to the real number of attackers (no double counting).
- [x] A Type-Tracked Ship with a small count still gets a named entry when larger non-tracked groups are present; the displaced group joins the "+N" overflow.
- [x] Group-matched groups gain no new slot priority; a group-only subscription's overall line and per-affiliation breakdowns are unchanged (regression assertion).
- [x] Type entries appear at their parent group's display position and on their parent group's category line.
- [x] Per-affiliation breakdown lines apply the same rule as the overall line.
- [x] Existing in-module slot-selection unit tests extended minimally for the type-priority rule; one embed-builder test for the mixed tally — no network; minimal coverage only.

## Comments

Chose an enum key, `TallyKey { Group(u32) | Type { type_id: u32, parent_group: u32 } }` (`src/discord_bot.rs`), threaded through `FleetComposition::overall` and `by_affiliation` (both now `Vec<(TallyKey, u32)>` / `Vec<(u64, u32, Vec<(TallyKey, u32)>)>`, previously keyed on bare `u32` group IDs). `TallyKey::parent_group()` centralizes the "classify/sort/display-position by parent group" rule used everywhere the old code used the group ID directly.

`select_top_groups` (the ticket-01-era, `u32`-keyed selector) is untouched byte-for-byte and still owns the known/unknown group partition. A new sibling, `select_top_entries(filtered: Vec<(TallyKey, u32)>, limit) -> Vec<(TallyKey, u32)>`, pulls type entries out first (sorted count DESC, tie-broken by `type_id`), takes up to `limit` of them, then calls `select_top_groups` on the remaining group entries for the leftover slots, and finally re-sorts everything by parent-group `GROUP_NAMES` position. With no type entries this reduces exactly to `select_top_groups(group_entries, limit)` — the regression guarantee is structural, not just tested by example.

`compute_fleet_composition` gained a `ship_type_ids: &HashSet<u32>` parameter (the same set ticket 01's `FilterNode::ship_type_ids()` produces); an attacker's flown `ship_type_id` (never the weapon) decides whether it tallies as `TallyKey::Type` or `TallyKey::Group`, so a type-tallied ship is never also counted in its group's bucket. `build_killmail_embed` now computes `ship_type_ids` once, before calling `compute_fleet_composition`, and reuses it for the title logic that already consumed it (ticket 01) — no recomputation.

`format_category_line_plain` and `format_category_line` now operate over `&[(TallyKey, u32)]`, filtering by `key.parent_group()` and calling a new `get_tally_entry_name` (Type → `get_name` on the type ID, always singular, matching the title's naming path; Group → unchanged `get_dynamic_group_name`). Line/prefix/separator formatting (`"{count}x {name}"`, `" └ {count} {name}"`, `"+{N}"`) is untouched.

Functions touched: `TallyKey` (new), `select_top_entries` (new), `get_tally_entry_name` (new), `FleetComposition` (field types), `format_overall`/`format_category_line_plain`/`format_category_line`/`format_alliance_breakdown` (signature: `u32` groups → `TallyKey` entries), `compute_fleet_composition` (new parameter + `TallyKey`-keyed maps), `build_killmail_embed` (reordered `ship_type_ids` computation ahead of the fleet-composition call).
