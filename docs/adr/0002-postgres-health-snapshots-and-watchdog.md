# Use PostgreSQL health snapshots with an independent Discord watchdog

The bot will persist bounded Health Snapshots and its Heartbeat in PostgreSQL, while an independent watchdog owns one persistent Discord Health View and one consolidated Health Incident in channel `1538030920328810536`. The watchdog may reuse the bot token and runs as a separately restartable Compose service. This keeps liveness reporting available when the bot process is dead, gives `/health` and Discord the same source of truth, and avoids deploying a separate Prometheus stack before time-series dashboards are needed; message and incident state remain restart-safe, and only Operator `146451271497416704` is eligible for a mention. `/health` follows the same authorization structure as the other commands. The initial configurable thresholds are: bot heartbeat 5/10 minutes, PostgreSQL first failure/three consecutive failures, contract progress 15/30 minutes, ESI progress 15/30 minutes beyond an expected pause, oldest due manifest or resolution backlog 30 minutes/2 hours while growing, prepared delivery 5/15 minutes, permanent delivery failure immediately critical, R2Z2 progress 3/10 minutes, and feed validation first failure/three consecutive failures, where each pair is degraded/critical. Health monitoring is observational: failure to initialize, evaluate, persist, or publish health must never gate bot startup, collection, matching, or delivery. This phase adds only the PostgreSQL tables and configuration necessary for health snapshots, transitions, heartbeat, and Discord message lifecycle; migration of existing JSON-backed Runtime State is explicitly deferred.
