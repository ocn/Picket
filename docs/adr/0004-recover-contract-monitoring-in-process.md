# Recover contract monitoring without deployment automation

The contract rollout will use a guarded Recovery Deployment to the sole production environment because the deployed ESI-progress query cannot become healthy and sweep-coupled terminal admission cannot drain the live backlog. Complete Retained Contract Manifests remain authoritative, while one single-consumer in-process Terminal Resolution Recovery loop reuses the existing PostgreSQL cases, public ESI client, persisted limiter, and durable delivery path. Recovery remains serial because the public contract-items route uses ESI's shared legacy error allowance: an acceptance-confirming `403` is an Error-Charged Probe even though it establishes a valid terminal outcome. The owner maximizes safe throughput by spacing error-charged probes, yielding at a reserved remaining-error floor, immediately reusing capacity after non-error-charged responses, and falling back to a slower spread cadence when authoritative headers are absent. Concurrency is deferred unless CCP provides an explicit route allowance because in-flight requests could overshoot the shared boundary without improving safe throughput. This deliberately adds no service, schema, worker pool, canary environment, traffic split, tuning variable, speculative page telemetry, automatic stop, automatic rollback, or automated remediation: the existing watchdog detects and reports regressions, subsequent rollout work stops, and production state changes only with operator direction. Historical Enrichment Repair remains separately gated by Production Verification and a fresh exact-count approval.
